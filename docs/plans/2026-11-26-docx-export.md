# DOCX export implementation plan

Add an editable Word download for a CV from the builder and from an application with a linked CV. Use the same saved content, template manifest, and customizations as the PDF export. The initial DOCX layout is a single column with native Word headings, paragraphs, and lists. Word controls wrapping and pagination.

## Output contract

- Use the resolved sections in saved section order. Preserve entry order and keep each employer, role, date range, and description together in reading order. Respect disabled sections, hidden headings, and the visible text the profile builder generates for contact links. Flatten template zones, two-column entries, and chips into text in the document body.
- Use A4 with 18 mm margins, 11 pt body text, a named title style for the candidate's name, and a heading style for visible section titles. Place contact details in the main body. Keep headings with their first content paragraph. Apply an explicit section page break to its first rendered paragraph when content precedes it. Let long entries flow across pages.
- Use the resolved text for dates, labels, and values. Preserve inline bold, italic, underline, and strikethrough, with native bullets and numbering for rich-text lists. Restart numbering for each numbered list. Preserve link labels and safe destinations, including authored query strings and fragments. Retain the label as text when the URL policy rejects its destination.
- Use the existing section builders for all data. Treat the Word layout as one fixed style across templates, with template and CV settings still contributing resolved content and semantic policy. In the export chooser, describe Word as an editable single-column document.

## Implementation sequence

### 1. Render Word from the resolved CV

1. Add `python-docx` to `api/pyproject.toml` after verifying the selected version against Python 3.12 and the API image's dependency install. Prototype writing an in-memory document with styled hyperlinks and two independent numbered lists. Use the documented APIs for paragraphs, runs, and byte-stream output. Use a small, tested WordprocessingML helper for hyperlink relationships and numbering when the supported API has no writer for those structures. [python-docx document API](https://python-docx.readthedocs.io/en/latest/api/document.html), [python-docx text API](https://python-docx.readthedocs.io/en/latest/api/text.html), [WordprocessingML styles](https://learn.microsoft.com/en-us/office/open-xml/word/how-to-create-and-add-a-paragraph-style-to-a-word-processing-document).
2. Add `api/app/services/renderer/docx.py` with a bytes-returning renderer that takes a `RenderModel`. In [the renderer pipeline](../../api/app/services/renderer/pipeline.py), share the model construction behind `resolve_source` and add a DOCX entry point that resolves with the Word renderer's capabilities. Keep the existing `DocumentRenderer.render()` string contract and the HTML capability response in `GET /api/v1/render/support`. Use the model's ordered section mapping so DOCX includes every enabled section once even when the CV places sections in separate zones.
3. Map resolved section headings, entry fields, runs, and rich-text blocks to the Word document body. Honor `SectionPolicy.show_title` and keep header fields in the same entry as their descriptions. Apply `api/app/core/safe_url.py` before writing link relationships. Replace XML-invalid characters while retaining Unicode text, tabs, and line breaks. Use neutral package metadata and build the file from a fresh in-memory document per request.

### 2. Expose the saved CV download

1. Add `api/app/services/docx.py` and a thin `POST /api/v1/cvs/{cv_id}/export/docx` route in [the CV router](../../api/app/routes/cvs.py). Reuse `CVService.get_cv(cv_id, user_id)` for the active, owned CV and `get_template_data` for its current manifest. Resolve the persisted sections and customizations through the shared pipeline. Carry the prepared input into a worker thread for synchronous document generation.
2. Return a binary response with media type `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, attachment name `cv-{cv_id}.docx`, and `Cache-Control: private, no-store`. Follow the PDF route's auth, CSRF, and 5/minute limit. Use the same 404 for missing, inactive, and unowned CVs. Return a generic 500 for a failed manifest lookup or generation and record only the error category in logs. Publish the binary media type in OpenAPI.
3. Use the existing [same-origin gateway](../../web/server/api/%5B...path%5D.ts) and verify it forwards the bytes and download headers. The export reads the current saved CV. Application detail exports `application.cv_id`, keeping the pending tailoring draft review flow separate.

### 3. Add Word to the existing export controls

1. Export an `exportDOCX(id): Promise<Blob>` function through [the CV feature's public entry point](../../web/src/features/cvs/index.ts). Follow the existing Axios blob request. Reuse [downloadBlob](../../web/src/shared/browser/downloadBlob.ts) and a safe filename derived from the visible CV title or application name, with `cv.docx` as the fallback.
2. Use a keyboard-accessible Export control with **PDF** and **Word (.docx)** in [the builder header](../../web/src/features/builder/components/BuilderHeader.tsx) and [the linked CV panel](../../web/src/features/applications/components/detail/ApplicationCvPanel.tsx). Keep the control compact at mobile widths. In the builder, await the existing explicit save before requesting the Word file. If save fails or the builder navigates to a different CV during save, stop the export. In application detail, use the same linked CV that the PDF action exports.
3. Guard repeat activation while a download is pending. Show progress and give failures a retryable state without discarding work. Keep the PDF endpoints, filenames, and builder save-before-export behavior.

## Acceptance and release

- **Renderer tests.** Reopen the generated file and inspect paragraphs, run properties, list numbering, and hyperlink relationships. Use synthetic fixtures that combine Unicode, long URLs, empty contact fields, disabled sections, hidden headings, reordered sections, duplicated dates, and populated entries from every builder. Test layouts with sidebar zones and local overrides. Assert order and association per entry as well as text retention. Verify that invalid links keep their labels and that numbering restarts after intervening paragraphs.
- **Route and gateway tests.** Verify the file reopens, the response headers survive the gateway, the download reflects the latest saved data, and access is denied for anonymous, foreign, and inactive CVs. Cover missing CSRF and a generation failure. Verify PDF preview and export regressions with the current renderer tests.
- **Browser and Word checks.** In Chromium, trigger each format with keyboard and pointer from the builder and application detail. Test immediate export after editing, save failure, navigation during save, and repeated activation. Open short, long, and multi-zone fixture exports in Microsoft Word and LibreOffice. Verify that they open without repair, headings stay with content, and users can edit, save, and reopen the file.
- **Release gate.** Run the backend suites for rendering, export, and OpenAPI, frontend lint and typecheck, architecture checks and fixtures, and `python dev.py --smoke`. Record the Word and LibreOffice versions used for the compatibility check and the results in the [tracker feature](../../tracker/features/FEAT-01M129QBNK54QF2Y9PV8WDKN8P-latex-docx-renderer-backends.md).
