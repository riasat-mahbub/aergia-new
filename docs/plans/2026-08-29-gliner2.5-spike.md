# GLiNER2.5 requirement extraction spike

This is an isolated feasibility spike. It does not change Aergia's
production extractor, matcher, Library selector, CV generation, persistence,
frontend, or deployment image.

## Scope

- Prototype the proposed `Requirement` contract.
- Run GLiNER2.5 small against representative synthetic job postings.
- Optionally compare the base checkpoint by changing `GLINER2_MODEL`.
- Add deterministic importance, years, degree, certification, and taxonomy
  enrichment.
- Compare the result with the current `requirement-v2` output.
- Measure model load, first/warm extraction latency, process CPU, RSS/peak RSS,
  and long-document extraction behavior.

The fixture corpus is intentionally small and is not a quality claim. It is a
repeatable gate for deciding whether a larger labeled evaluation is warranted.

## Local contract-only checks

The prototype has no GLiNER dependency in the normal API environment. Run its
unit tests without the repository integration fixture setup:

```bash
PYTHONPATH=api api/.venv/bin/pytest --noconftest -q api/tests/test_gliner2_spike.py
```

The deterministic baseline can run without model dependencies:

```bash
PYTHONPATH=api api/.venv/bin/python -m scripts.gliner2_spike \
  --mode baseline --repeat 1
```

## Production-derived Docker benchmark

The runner builds `api/Dockerfile` first and layers the pinned GLiNER2 package
and downloaded model into a separate ephemeral image. It installs a CPU-only
PyTorch wheel explicitly; the generic `gliner2[local]` dependency otherwise
resolves CUDA component wheels on the current package index. It also pins
Transformers for the current checkpoint tokenizer compatibility. The default limit is the
documented deployment target of one CPU and one GiB RAM:

```bash
api/scripts/run_gliner2_spike_docker.sh > /tmp/gliner2-small.json
```

Compare the base checkpoint separately:

```bash
GLINER2_MODEL=fastino/gliner2.5-base-v1 \
  api/scripts/run_gliner2_spike_docker.sh > /tmp/gliner2-base.json
```

Useful overrides:

```bash
GLINER2_MEMORY=2g GLINER2_CPUS=2 GLINER2_REPEAT=3 \
  api/scripts/run_gliner2_spike_docker.sh
```

The output contains per-case requirements, requirement-v2 diffs, quality
measurements, model-load timing, short/long inference path, CPU time, RSS,
peak RSS, and container limits.

## Observed run (2026-08-29)

The benchmark used the production-derived Docker image, Python 3.12.14,
`gliner2==2.0.0`, CPU-only `torch==2.9.1+cpu`,
`transformers==4.51.3`, one cgroup CPU, and one process-local model. The
fixture has four evaluated synthetic postings (19 expected requirements) plus
a 4,160-word repeated posting used only for long-document stress. It is useful
for feasibility and regression checks, not a production quality estimate.

| Run | Precision | Recall | Importance | Constraints | False required | Split / merge |
|---|---:|---:|---:|---:|---:|---:|
| requirement-v2 | 58.6% | 89.5% | 100% | 16.7% | 0 | 5 / 1 |
| GLiNER2.5-small | 90.9% | 52.6% | 87.5% | 100% | 0 | 1 / 1 |
| small + v2 comparison merge | 72.0% | 94.7% | 100% | 55.6% | 0 | 2 / 1 |
| GLiNER2.5-base | 83.3% | 26.3% | 75% | n/a | 0 | 1 / 1 |
| base + v2 comparison merge | 68.0% | 89.5% | 100% | 16.7% | 0 | 2 / 1 |

The small checkpoint identified useful prose requirements and improved the
comparison merge's recall, but missed isolated preferred skills such as
Kubernetes, AWS, dbt, and Playwright. The base checkpoint did not improve the
fixture result and produced fewer semantic candidates. The hybrid rows are
comparison-only output; they are not a production algorithm recommendation.

Resource observations under a hard cgroup limit:

| Checkpoint | Limit | Cold load | Load peak RSS | Warm short extraction | Long stress | Long peak RSS |
|---|---:|---:|---:|---:|---:|---:|
| small | 1 GiB | OOM (exit 137) | — | — | — | — |
| small | 2 GiB | 6.45 s | ~1.08 GiB | 0.36–0.51 s | 17.97–17.99 s | ~1.44 GiB |
| base | 2 GiB | OOM (exit 137) | — | — | — | — |
| base | 3 GiB | 7.34 s | ~1.95 GiB | 1.13–1.32 s | 53.43 s | ~2.41 GiB |

The process used roughly 90% of the one-CPU allocation while loading and
96–99% during warm extraction. The small model's post-load RSS was about
0.84 GiB; the base model's was about 1.23 GiB. The long path completed with
384-word chunks and 64-word overlap, but the repeated stress document was not
quality-scored. Chromium was present in the production-derived image but was
not launched concurrently during this isolated model measurement, so the
memory target below intentionally includes safety margin.

The observed Docker image virtual sizes were approximately 3.96 GB for the
small spike image and 4.88 GB for the base spike image, versus 1.99 GB for the
production image before the model runtime layer. The model cards list 74M
parameters / approximately 296 MB FP32 weights for small and 194M parameters /
approximately 407 MB weights for base. Both the `gliner2` package and these
checkpoint cards declare Apache-2.0 licensing; transitive runtime dependencies
still need the normal application license audit before production adoption.

The measured conclusion is to retain `requirement-v2` as the production
extractor for now, with targeted parser improvements, while keeping
GLiNER2.5-small as a candidate semantic-assist implementation for a larger
real-posting evaluation. It is not ready to replace the parser based on this
fixture. If it becomes a production dependency, a small-model deployment
should target at least 3 GiB RAM on a 1-vCPU VPS, with 2 vCPUs preferable for
concurrency; the base model should be treated as a 4 GiB-plus, 2-vCPU option
and is not recommended for the documented low-cost target.

The measured small checkpoint was resolved to
`cab1bddfd30fda7b803a4691c41f90378a2d517a`; the base comparison resolved to
`72ac19b486cd4557424c8d61114e7530c243e9b0`. Future reruns should pass these
revisions explicitly rather than relying on the Hub default.

## Decision gate

Do not integrate the prototype based on extraction count alone. The next
decision should consider, together:

1. recall of prose requirements;
2. invented requirements and false `required` classifications;
3. constraint and importance accuracy;
4. split/merge behavior and source-span fidelity;
5. warm latency and cold load time;
6. peak RSS under 1 GiB and a realistic higher-memory limit;
7. behavior on the repeated long-document fixture.

The decision options are: ship small, use base, retain requirement-v2 with
targeted improvements, or pursue another extractor.
