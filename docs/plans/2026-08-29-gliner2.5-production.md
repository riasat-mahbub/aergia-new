# GLiNER2.5-small requirement extraction

## Decision

Use `fastino/gliner2.5-small-v1` as the sole production requirement extractor.
The selected revision is pinned to
`cab1bddfd30fda7b803a4691c41f90378a2d517a`. The old deterministic
`requirement-v2` parser remains available only as an explicit comparison/test
helper; production requests do not silently fall back to it.

## Runtime boundary

`app.services.requirement_extractor` owns model loading, semantic candidate
discovery, deterministic enrichment, source-span normalization, exclusion
filtering, deduplication, and adaptation to the existing `JobRequirement`
schema. The relevance service and application generation path receive that
adapter output and retain their existing matching, Library selection, fitting,
rendering, snapshot, and SQLite behavior.

The model is asked for complete candidate requirement spans plus hard skills,
experience, education, certification, responsibility, preferred, quantitative,
and domain concepts. Section headings, company prose, pay, benefits, legal
boilerplate, and generic location/remote prose are removed during normalization.
Explicit years, degree, certification, required/preferred, negation, and work
eligibility signals remain deterministic. Unknown importance is never promoted
to required.

Short descriptions use one model call. Longer descriptions use GLiNER2's
overlapping long-document path with 384-word windows and 64 words of overlap;
the source sentence/section context is retained for exclusion, enrichment, and
span normalization, with a sentence/section-aware manual fallback for model
adapters without a native long-document method. Spans are remapped to the
original source and deduplicated. One process-local model singleton is loaded
lazily; an inference lock limits concurrent calls to one.

## Failure behavior

Model import, load, inference, empty-result, and invalid-result failures raise
`RequirementExtractionError`. Application create/update/recompute/generation
and linked-CV relevance refresh return the stable extraction error to the API;
they do not persist an empty extraction or invoke `requirement-v2`.

## Deployment

The production Docker image installs CPU-only PyTorch and the pinned model
dependencies, then downloads the model artifact during image build. Runtime
initialization is still lazy. The preferred host target is 8GB RAM and 2+
vCPUs. The measured small-model lower bound is approximately 3GB RAM with one
serialized CPU, leaving limited room for Chromium and long descriptions. Do
not increase Uvicorn worker count without budgeting one model copy per worker.

The included representative fixture measured approximately 6.2 seconds for
cold model loading, 2.7–3.6 seconds for warm short postings, and 1.13GB peak
RSS during load in an 8GB/2-vCPU container. A 4,160-word long case used the
native long path in about 91.7 seconds and peaked at 1.64GB RSS. These are
capacity measurements, not latency guarantees for arbitrary postings.

## Verification

Normal pytest tests use a deterministic test double and never import the real
model. `tests/test_requirement_extractor.py` tests the production boundary
with mocked model output. The optional integration/evaluation suite accepts an
operator-supplied JSON fixture containing manually annotated real job
descriptions, so private postings do not enter the repository:

```bash
RUN_GLINER2_INTEGRATION=1 \
GLINER2_EVAL_FIXTURES=/secure/path/annotated-jobs.json \
pytest -m integration tests/integration/test_gliner2_model.py
```

The evaluation reports missing/invented requirements, false required
qualifications, importance and constraint accuracy, and split/merge signals.
